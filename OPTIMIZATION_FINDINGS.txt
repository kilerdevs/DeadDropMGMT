Method: 4 read-only review agents, one per area:

  - maps / proxy / tiles
  - frontend / assets / server configs

BUGS FOUND DURING THE REVIEW (confirmed in the code)
----------------------------------------------------------------------

B1 [HIGH] PMTiles run-length lookup treats tiles as missing
  Where: includes/pmtiles.php:956 (pmtiles_lookup_id)
  Problem: The function ends with `return $cand['id'] === $id ? $cand : null;`.
    Tiles inside a run-length entry (run > 1) are therefore reported as
    missing. Runs are how PMTiles stores identical tiles, such as open sea
    or uniform land.
  Effect: Zones built by the pure-PHP engine probably have holes over
    water and other uniform areas.
  Fix: Match when $cand['id'] <= $id < $cand['id'] + $cand['run'].

B2 [HIGH] cleanup_expired_orders can loop forever
  Where: includes/order_state.php:140-183
  Problem: The do/while loop keeps going while the SELECT returned a full
    batch (count === $batch), not while it made progress. If 200 or more
    expired rows fail every time (the exception path rolls back and leaves
    them expired), the same rows come back on every pass.
  Effect: Under FPM this runs after the response with
    ignore_user_abort(true). Time spent waiting on the DB mostly doesn't
    count toward max_execution_time, so it can spin for a very long time.
  Fix: Stop when a pass deleted 0 rows, or page forward by id
    (AND id > ? ORDER BY id). Also prepare the lock, photo and delete
    statements once, outside the foreach.

H1 [HIGH] Proxy: tile cache misses can take every PHP worker
  Where: includes/proxy.php:881-906 (osm_fetch), :686-693 (osm_fetch_via)
  Problem: One map view fires 15-30 tile requests in parallel. Each tries
    proxies one after another (3 s per proxy, up to 20 s in total).
    Concurrent requests all pick the same dead proxy first, because it is
    only marked failed after its attempt finishes. With about 5 FPM
    workers, the whole admin panel stalls.
  Fix: Record a shared "pool down until T" time (settings row or APCu),
    set when every proxy fails, so later requests return 502 at once.
    Cut the connect timeout to about 1-1.5 s and the total to about 3 s.
    Cache failed tiles for about 30 s.
    Optional: race the top 2 proxies with curl_multi. Privacy trade-off:
    two proxies then see the tile coordinates instead of one.
  Impact: Worst case per tile drops from about 20 s to near zero while
    the pool is down.

H2 [HIGH] maps_action.php keeps the session lock during long work
  Where: admin/maps_action.php:8, 55, 79, 96, 104
  Problem: maps_php_poll_slice() (8 s or more) and maps_php_inline()
    (up to 25 s) run without session_write_close(). The status poll runs
    every 3 s (settings.php:923). Every other admin request from that
    owner, tiles included, waits behind it for the whole download.
  Fix: Call session_write_close() before the slice or inline run.
    json_out() reopens the session when it needs the CSRF token.
  Impact: The admin UI stops freezing during map downloads.

H3 [HIGH] Maps: sizing has no overall time limit and cannot resume
  Where: includes/maps.php:1583-1600, includes/pmtiles.php:299-361
  Problem: pmtiles_build_plan walks every leaf directory one after
    another. If it goes past max_execution_time, the fatal error discards
    all the work and skips maps_worker_unlock(). The next attempt waits
    MAPS_WORKER_STALL_SECS (45 minutes), and the cycle can repeat.
  Fix: Work out the needed leaf pointers from the root directory and
    combine neighbouring leaves into a few range requests. Save the raw
    leaf bytes to a sidecar file so sizing can resume. Register a shutdown
    function that releases the lock.
  Impact: Dozens of sequential requests become a handful, and a failed
    attempt no longer locks the queue for 45 minutes.

H4 [HIGH] Maps: leaf-directory cache can run out of memory
  Where: includes/pmtiles.php:333-353, 828-896
  Problem: Every parsed leaf stays in memory as arrays of 4-key
    associative arrays (about 400 B per entry). A city extract touches
    10-15 leaves of the planet file, possibly hundreds of MB against a
    128M memory_limit (estimate).
  Fix: The wanted IDs are sorted, so keep only the current leaf. Parse
    into packed integer lists (or SplFixedArray) instead of per-entry
    arrays.
  Impact: Peak memory drops to a few MB. Confirm with
    memory_get_peak_usage.

H5 [HIGH] Frontend: nginx and Caddy setups compress nothing
  Where: docker/nginx.conf, docker/Caddyfile
  Problem: The stock nginx:alpine config has "#gzip on;" commented out,
    and Caddy needs an explicit "encode" line. Uncompressed sizes:
      maplibre-gl.js  1,015,688 B  (about 265 KB gzipped)
      admin/style.css 65 KB        (about 12 KB gzipped)
      style.css       24 KB        (about 4.7 KB gzipped)
    HTML pages are sent uncompressed too.
  Fix:
    Caddy: add "encode zstd gzip" in the :80 block.
    nginx: add
      gzip on; gzip_comp_level 5;
      gzip_types text/css application/javascript image/svg+xml
                 application/json application/x-protobuf;
    Do NOT compress /uploads or .pmtiles. Tile data is already compressed,
    and compression breaks Range requests.
  Impact: About 750 KB less per first map reveal, on the recipient's
    phone.

H6 [HIGH] Frontend: full-size photos are used as 140 px thumbnails
  Where: index.php:409-411, admin/edit.php:432,
    includes/crypto.php:518-590 (_compress_image), style.css:447-454
  Problem: Photos are only shrunk when they're over max_photo_mb
    (default 2 MB). The resolution cap is 16 MP. The public grid (140 px
    tiles) and admin thumbnails load the full file, so 6 photos can mean
    about 12 MB on mobile. Compression can re-encode a full-resolution
    image up to 10 times in fixed 0.15 scale steps (PNG only ever scales
    down).
  Fix: Cap the longest edge (for example 2560 px) before the quality
    loop, and estimate the next scale from the size ratio,
    sqrt(max/size)*0.95. Save a thumbnail of about 400 px at quality
    about 75, with its own random name. The grid uses the thumbnail and
    the lightbox uses data-full (gallery.js:32).
  Trade-off: A second file per photo. Order delete, panic wipe and
    cleanup must also delete it.
  Impact: 10-50x fewer bytes for the grid, and 1-2 encodes instead of
    up to 10.

H7 [HIGH] CI: Grype vulnerability DB is downloaded fresh every run
  Where: .github/workflows/ci.yml:382-389
  Problem: The Apache scan step takes 91-103 s, of which about 36 s is
    downloading the DB and about 54 s is installing it.
  Fix: Add cache-db: true to both anchore/scan-action steps.
  Impact: About -80 s on the slowest job.

H8 [HIGH] CI: the docker job runs every step one after another
  Where: .github/workflows/ci.yml:358-490
  Problem: The job takes 266-331 s, against 83-124 s for the slowest
    test job. Steps: build 26+22 s, Grype 103+15 s, SBOM 15 s, three
    smoke tests 36 s, ZAP 69 s (34 s of it pulling the ZAP image).
  Fix: Split into parallel jobs:
      image-scan: build, Grype, SBOM
      smoke-dast: build, compose smoke tests, ZAP
    Build with docker/build-push-action and cache-from/to type=gha, one
    scope per Dockerfile, load: true. Keep an aggregate job named
    "docker", because branch protection requires that check name.
  Impact: About -150 s of total run time.

H9 [HIGH] CI: no concurrency setting, so duplicate runs pile up
  Where: .github/workflows/ci.yml:3-6, .github/workflows/sast.yml:8-12
  Problem: The same commit runs under both push:dev and pull_request. A
    release produces 3 full 13-job runs. Overlapping runs hit the job
    limit: test jobs waited 49-64 s in the queue in run 36345330215.
  Fix:
    concurrency:
      group: ${{ github.workflow }}-${{ github.event.pull_request.number || github.ref }}
      cancel-in-progress: ${{ github.ref != 'refs/heads/master' }}
    Consider running push only for master and relying on pull_request
    for dev.

M1 [MEDIUM] DB: hourly purge of old events joins on an OR condition
  Where: includes/cleanup.php:34-38
  Problem: The DELETE uses
      LEFT JOIN orders o ON o.id = e.order_id OR o.token_hmac = e.token_hmac
    which can't use an index, so each old event is compared against the
    whole orders table. There is no LIMIT, so one statement locks every
    matching row. order_events is fed by unauthenticated lookups (one row
    per unknown-token POST, index.php:141).
  Fix: Use two NOT EXISTS checks (orders.id, orders.token_hmac; both
    indexed) and delete in batches (LIMIT 5000, repeat while rows are
    affected).

M2 [MEDIUM] Panic wipe: memory blowup, and sensitive files wiped last
  Where: config.php.example:132, includes/wipe.php:73/77/88,
    admin/panic.php
  Problem: fwrite($fh, str_repeat("\0", $size)) allocates each file's
    full size in RAM. A large backup dump can hit the 256M limit with an
    uncatchable fatal error. The tile cache (one fsync per file, maybe
    thousands) is wiped before backups and logs, which hold IPs and
    tokens. panic.php sets neither ignore_user_abort nor set_time_limit.
  Fix: Write zeros in 1 MiB chunks. Wipe logs and backups first, then
    photos, then the tile cache. Add ignore_user_abort(true) and
    set_time_limit(0) in panic.php. This makes the wipe more reliable,
    not weaker.

M3 [MEDIUM] DB: analytics page runs 7 queries, some redundant
  Where: admin/analytics.php:48-128
  Problem:
    - $total_events (:112) equals array_sum($counts) from :48.
    - COUNT(DISTINCT ip_address) (:57) can be folded into the same pass.
    - event_type NOT LIKE 'admin_%' (:50, 59, 70, 86, 114, 125 and
      settings.php:60) can never match. The only types written are
      lookup, unlock_success, unlock_fail and received.
  Fix: Remove the redundant filter and COUNT. Add
    INDEX (event_type, created_at, ip_address), which covers the
    "suspicious IPs" and "unlock IPs" queries (:95, :104).

M4 [MEDIUM] DB: orders list has no pagination
  Where: admin/orders.php:61-80
  Problem: No LIMIT, GROUP BY with a sort, and an AES-GCM decrypt of the
    token for every row. Preparing orders never expire, so the list only
    grows.
  Fix: Paginate like audit_log.php. Add INDEX (created_by, created_at)
    for the courier view.

M5 [MEDIUM] Logs: viewer and integrity check read whole files into memory
  Where: includes/logger.php:368-379 (log_recent_entries),
    :635-649 (verify_log_continuity), admin/log_verify.php:25-27
  Problem: file() loads up to about 10 MB of JSON lines, decodes all of
    them and keeps every entry. log_verify then reads the same files twice
    (once for the hash chain, once for continuity). The viewer loads 5 MB
    to show 200 lines.
  Fix: Track min/max sequence numbers and the checkpoint hash while
    streaming in _verify_log_file, so one pass is enough. For the viewer,
    read backwards from the end like log_tail_lines().

M6 [MEDIUM] Static files: no caching policy or version tags
  Where: .htaccess, docker/apache.conf, docker/nginx.conf:47-50,
    docker/Caddyfile, includes/version.php:88
  Problem (verified live): /style.css, /maplibre/*.js, fonts and glyphs
    have no Cache-Control header, so browsers keep checking or keep stale
    copies. Only admin/style.css has a version tag (admin_css_ver). An
    admin can get new CSS with old admin.js after an update.
  Fix: Turn it into asset_ver($path) and add ?v= to every first-party
    <script> and <link>. Send "Cache-Control: public, max-age=31536000,
    immutable" for /maplibre/, /admin/vendor/, /fonts/ and ?v= requests.
    Keep /uploads on no-store. Choose one explicit policy for *.pmtiles
    and glyphs (no-store to match the uploads rule, or private max-age
    with ETag) and use it in all three server configs.

M7 [MEDIUM] Frontend: MapLibre (1 MB) loads before the map is wanted
  Where: index.php:543-545
  Problem: On low-end phones, parsing about 1 MB of JS costs a few
    hundred ms of main-thread time, even if the recipient never looks
    at the map.
  Fix: reveal-map.js adds the maplibre-gl.js and pmtiles.js script tags
    when #reveal-map scrolls into view (IntersectionObserver) or on a tap.
    This works under the existing CSP (script-src 'self').

M8 [MEDIUM] Apache: SVG and .pbf are not compressed; .pbf has no type
  Where: .htaccess:18-28 (and :11)
  Problem (verified live): Glyph sizes would drop 76 KB -> 46 KB and
    128 KB -> 62 KB with gzip.
  Fix: AddType application/x-protobuf .pbf, and
    AddOutputFilterByType DEFLATE image/svg+xml application/x-protobuf.
    Also check the static-file allowlist at :11: it doesn't list pbf,
    pmtiles or json, so hosts that deny by default could return 403 for
    them.

M9 [MEDIUM] osm_monit polls every 5 s forever, including hidden tabs
  Where: admin/osm_monit.php:58-71 (also mzPoll in settings.php:923)
  Problem: One authenticated request every 5 s per open map tab. tick()
    re-arms setInterval, so slow responses overlap. Side effect:
    require_admin rewrites login_time, so an open tab keeps the admin
    logged in indefinitely.
  Fix: Chain setTimeout calls, pause while document.hidden, and poll
    only after tile or geocode activity.

M10 [MEDIUM] Maps: PMTiles range requests don't reuse connections
  Where: includes/pmtiles.php:216-253, includes/proxy.php:531
  Problem: A new curl handle for each range means a new TCP, proxy and
    TLS handshake every time. The path without curl sends
    Connection: close.
  Fix: Keep one curl handle per plan or fetch run. PHP 8.5 can also
    reuse connections across requests with curl_share_init_persistent.
  Impact: About 0.3-2 s saved per request on public proxies.

M11 [MEDIUM] Maps: plan file decoded and validated twice every slice
  Where: includes/maps.php:1583, 1617; includes/pmtiles.php:699-791
  Problem: With up to 250k entries, each 8 s slice does a large
    json_decode and two full validations.
  Fix: Store spans and metadata separately from entries, load entries
    only when assembling, and store them packed (pack('P*')). Skip the
    second validation.

M12 [MEDIUM] Maps: PHP engine output layout
  Where: includes/pmtiles.php:477-503, 509-618
  Problem: All entries go into one root directory (well past the 16 KB
    guideline in the spec), so the browser must fetch and decode the whole
    directory before the first tile. Tiles that share an offset in the
    source are copied again for every entry.
  Fix: Build leaf directories like go-pmtiles, reuse the output offset
    for entries with the same source offset, and use run lengths.
    Do this together with B1.

M13 [MEDIUM] Proxy: discovery runs sequentially
  Where: includes/proxy.php:1101, :1198; cron/proxy_heal.php:31
  Problem: The 9 proxy lists are downloaded one after another. The
    anonymity check calls proxy_judge_anonymous per proxy (2 judges x 6 s)
    after the parallel round, with no cap in CLI mode. set_time_limit(300)
    can kill the heal job midway and leave its lock held for 15 minutes.
  Fix: Fetch the lists in parallel with curl_multi. Read bodies from the
    parallel round (curl_multi_getcontent) and run the second judge as
    another parallel round. Privacy is unchanged; these requests are
    already direct.

M14 [MEDIUM] Maps: reverse-geocoded pin label is never cached
  Where: admin/pin-label.js:226-241, admin/geocode_proxy.php:116-134
  Problem: Every pin click or drag and every edit.php load makes a full
    proxied Nominatim request (up to 20 s) and uses the 60-per-minute
    budget.
  Fix: Add a server cache per account, keyed by coordinates rounded to
    0.01 degrees, with a long lifetime (per account for the timing reason
    at tile_proxy.php:41-44). In the browser, round before sending, keep
    a label cache, and cancel the previous request with AbortController.
    Rounding is also a privacy gain: exact coordinates stop appearing in
    access logs.

M15 [MEDIUM] Tests: ArrayInputTest is 22% of the suite (12.9 s of 59 s)
  Where: tests/ArrayInputTest.php:131-166
  Problem: More than 2,000 requests are sent one at a time, plus a CSRF
    GET before every POST (the token rotates, auth.php:465).
  Fix: Send one request per (endpoint, method) with every name as
    name[]=x, and bisect per name only on failure. About 70 requests
    instead of about 3,000.
  Caveat: An early-exit guard on one parameter could hide a crash path
    on another.
  Impact: About -11 s in each of the 6 test jobs, plus coverage.

M16 [MEDIUM] Tests: PseudoCronTest spends 4.5 s of 5.0 s in fixed sleeps
  Where: tests/PseudoCronTest.php:94, 101, 111
  Problem: Three usleep(1500000) negative checks.
  Fix: The sweep runs in a shutdown function and php -S handles one
    request at a time, so a follow-up GET /healthz.php only returns after
    the previous sweep finishes. Use it as an exact wait instead of the
    sleeps.
  Impact: About -4.4 s per job, and one less timing-based flake.

M17 [MEDIUM] Tests: the runner is fully serial
  Where: tests/run_all.php:23-31 (45 suites, 59 s)
  Fix: Run N workers, each with its own DDMGMT_TEST_DB
    (deaddrops_test_$i). The logs, session and cache directories must be
    per worker, or suites that use them stay in a serial group.
  Impact: About 59 s -> 20 s (estimate).

M18 [MEDIUM] Docker: SBOM ends up in the tested image; .dockerignore gaps
  Where: ci.yml:407, 414; .dockerignore
  Problem: The SBOM steps write sbom-*.cdx.json into the workspace. The
    next "compose up --build" then misses the cache at COPY ., so the
    image that is smoke-tested and ZAP-scanned serves
    /sbom-apache.cdx.json from its docroot and differs from the image
    Grype scanned.
    .dockerignore misses: tiles/*.pmtiles, data/maps/*, node_modules/,
    e2e/, test-results/, playwright-report/, coverage-html/, *.phar,
    package*.json, playwright.config.js, phpstan.neon, .php-cs-fixer.php,
    composer.json, .semgrep*, fromftp/, .claude/.
  Fix: Write SBOMs to ${{ runner.temp }} and extend .dockerignore. Give
    the compose app and fpm services an image: tag so the scanned image
    is the one tested.

M19 [MEDIUM] Docker: runtime images keep the -dev packages
  Where: Dockerfile:11-21, Dockerfile.fpm:10-19
  Problem: libfreetype6-dev, libjpeg62-turbo-dev, libpng-dev and
    libwebp-dev are never purged.
  Fix: After building the extensions, apt-mark manual the runtime
    libraries and apt-get purge --auto-remove the -dev packages, or use a
    multi-stage build.
  Impact: 30-60 MB per image (not measured), and fewer packages for
    Grype and Syft to scan.

M20 [MEDIUM] Tools: key rotation fully scans audit_log once per order
  Where: tools/rotate_aes_key.php:214-218; setup.sql:340-359
  Problem: It runs UPDATE audit_log ... WHERE token_hmac = ? once per
    order, and audit_log.token_hmac has no index. The cost is
    orders x audit rows, inside one FOR UPDATE transaction.
  Fix: Add a guarded idx_token_hmac on audit_log, or do one UPDATE
    joined against a temp mapping table. Move the prepare() calls
    (:191, :219) out of the loops.

M21 [MEDIUM] CI: no path filters
  Where: .github/workflows/ci.yml:3-6
  Problem: A docs-only change (README, CHANGELOG, docs/) runs all 13
    jobs, including Docker and ZAP.
  Fix: Use paths-ignore, or a dorny/paths-filter gate job so required
    checks don't sit pending.

M22 [MEDIUM] CI: no layer cache for Docker builds
  Where: .github/workflows/ci.yml:371-375
  Problem: The apt layer and the gd compile cost 26-40 s plus 22-26 s
    on every run.
  Fix: Use the GHA cache (goes with H8). Bust the apt-get upgrade layer

LOW
----------------------------------------------------------------------

L1  Rate limiting takes 4-5 DB round trips (includes/auth.php:651-708).
    BEGIN, SELECT FOR UPDATE, UPDATE and COMMIT run twice per public
    unlock POST. A single INSERT ... ON DUPLICATE KEY UPDATE with
    IF(window_start < cutoff, ...) plus one read is atomic with no
    transaction. Keep the fail-closed handling of bad window_start
    values.

L2  Schema indexes (setup.sql):
    - users.idx_username (:42) duplicates the UNIQUE key on username.
    - order_events.idx_ip (ip_address(20)) (:304) is never used in a
      WHERE, and a prefix index can't serve GROUP BY.
    - idx_event_type (:303) has 4 distinct values and becomes redundant
      once M3's index exists.
    Every extra index is paid on every public log_event insert.

L3  Every request loads all 19 modules (includes/kernel.php:29-51),
    including proxy.php, maps.php and pmtiles.php (about 4.7k lines).
    This is cheap with OPcache, but shared hosts may not have OPcache.
    Load the map and proxy modules only where needed.

L4  Each log write opens and locks two files (includes/logger.php:
    211-257): app.log.lock for rotation, then app.log. One lock across
    rotate and append halves the cost and closes the gap between the two
    steps. Cleanup also writes one log_info per deleted order
    (order_state.php:174); one summary line per pass would do.

L5  Photos are processed inside the open DB transaction
    (admin/create.php:91-141). Process the images first, then run a short
    transaction.

L6  The settings page reloads the already-cached settings table
    (admin/settings.php:49), and runs a full COUNT(*) and a
    COUNT(DISTINCT token_hmac) on order_events on every view, just for a
    warning label (:60-61).

L7  Each tile miss causes two writes. osm_proxy_mark UPDATEs on every
    attempt (proxy.php:892), and osm_last_via_flush (:996, called from
    tile_proxy.php:71) rewrites the session. Write only when the status
    changes or when last_checked is older than 60 s.

L8  The prober without curl busy-waits (proxy.php:1309-1321): connected
    sockets stay writable, so stream_select spins until connectDl. Drop
    finished sockets from the set. Latency at :1334 is measured from the
    start of the batch, so proxies handled later look slow, fail the
    3000 ms cut, and the ranking comes out wrong.

L9  The tile cache has no 304 support and writes non-atomically
    (admin/tile_proxy.php:48-53, 89). Send ETag/Last-Modified, set
    max-age to the remaining lifetime, and write via temp file + rename.

L10 maplibre-picker.js:149 fetches /tiles/style.php before creating the
    map. Embed it as data-style like reveal-map.js does.
    addTextAttribution is duplicated (reveal-map.js:37-49 and
    maplibre-picker.js:132-144).

L11 Chunked HTTP decoding re-parses and copies the full buffer on each
    read (proxy.php:202-222), which gets slow for multi-MB chunks. Keep a
    parse offset. Rarely hit, since 206 responses use Content-Length.

L12 Leaflet (148 KB) always loads on the settings page
    (admin/settings.php:494-495), even in self-hosted mode or when the
    zone editor isn't shown. Wrap it in the #mz-map condition. Longer
    term, MapLibre can display tile_proxy raster tiles, so Leaflet could
    be dropped.

L13 Pre-compress maplibre-gl.js (.br/.gz: Caddy precompressed, nginx
    gzip_static, Apache rewrite) to save CPU and about 15-20% more bytes.
    In Docker only, opcache.validate_timestamps=0 and
    realpath_cache_ttl=600 are safe (docker/php-ddmgmt.ini). Don't set
    them for shared hosting or auto-update installs. AllowOverride All
    (docker/apache.conf:10-12) makes Apache look for .htaccess files on
    every request; only worth changing under load, since the rules would
    then exist twice.

L14 The admin countdown (admin/admin.js:7-30) runs querySelectorAll and
    rewrites className for every row every second. Query once and write
    only on change.

L15 CI speedups:
    - Playwright: install only the Chromium headless shell
      (--only-shell chromium) and cache ~/.cache/ms-playwright
      (about -10 s).
    - Lint step (ci.yml:61): run in parallel with xargs -P$(nproc)
      (6 s -> 1.5 s, in 4 jobs).
    - Poll for php -S readiness every 50 ms instead of 200 ms, and drop
      the extra fixed 200 ms in the installer tests
      (InstallerTest.php:59).

L16 CI tests on mariadb:11 and mysql:8.0, but the shipped compose file
    runs mariadb:13, so the version that ships is never tested. Fold
    tests-mysql and tests-tz into matrix include: rows (13 -> 11 jobs).
    Run the report-only mutation probe only on dev pushes or on a
    schedule. Pin the ZAP image by digest.

L17 Docker: Dockerfile.fpm:36 copies the app a second time
    (cp -a /var/www/html /usr/src/ddmgmt); copy straight to
    /usr/src/ddmgmt. COPY tests/schema_loader.php is redundant
    (.dockerignore:8 already includes it). docker/entrypoint.sh:68 runs
    chown -R over the whole tile cache on every start; use
    find ! -user www-data -exec chown.

L18 Dependabot: no npm entry, so @playwright/test is never bumped. No
    groups, so every bump is a full 13-job CI run. The comment at line 24
    still says "Trivy".

L19 The installer-min commit-back job (ci.yml:499-534) duplicates the
    InstallerMinTest freshness check. When the file is stale, the suites
    already fail, so the commit-back only runs on red builds and races
    dev pushes. Keep one of the two.

L20 The GET ?token= lookup (index.php:68-89) has no rate limit and logs a
    lookup event, unlike the POST path and receive.php. Guessing isn't
    feasible (about 82-bit tokens). Spend the public limit here too, or
    drop the event insert.

L21 The admin POST flow fetches a fresh CSRF token before every submit
    (admin/admin.js:49-73), adding one round trip. This is deliberate
    (the token rotates after each use), so keep it. Optionally, fetch
    only when another request has already used the rendered token.

- Settings are loaded once per request (includes/settings.php:16).
- Derived keys are cached (includes/crypto.php:50).

  shift.

  DB writes are throttled. net.php is fine.
- DB migration tools: fetchAll on small tables inside all-or-nothing
  transactions is fine; batching isn't worth it.
- Kept deliberately for security:
  - bcrypt cost 12 and the dummy-hash verify
  - the users read on every request in require_admin()
  - CSRF token rotation
  - the session on public pages
  - zero-overwrite on delete
  - no-store on HTML pages (which also disables the back/forward cache)
